## ORC-T7: two `analystos driver` processes, one killed mid-run — takeover, 25/26

Same plane, with `ANALYSTOS_RUN_DRIVER=process` and `ANALYSTOS_DRIVER_LEASE_SECONDS=10` on the API and on two
`analystos driver` processes (`ANALYSTOS_ORCHESTRATOR=langgraph`). `/api/health`: `checks.orchestrator` up,
`run_driver: process`, both drivers listed from `run_driver` heartbeats. The API drove nothing itself: starts,
approvals, the pause/resume and the feedback only woke runs (`run_lease.wake_at`).

`scripts/e2e_demo.py` ran on top ([`e2e-20261030-055905.md`](e2e-20261030-055905.md), run `run_02ac61fbeb7f`). A helper
watched `run_lease` and, once three steps had completed, **hard-killed the driver holding the run**
(`taskkill /T /F`) while `relationships` and `profile` ran. Raw timeline: [`orc-t7-takeover-20261030.json`](orc-t7-takeover-20261030.json).

| t after the kill (s) | Lease holder | Epoch | Run status |
|---|---|---|---|
| 0.6 | driver A (killed) | 1 | RUNNING |
| 11.3 | driver B ("took over run run_02ac61fbeb7f (epoch 2)") | 2 | RUNNING |
| 427.8 | none (parked at the publication approval) | 2 | WAITING_USER |
| 429.0 | none (re-claimed on the pause, parked again) | 3 | PAUSED |
| 433.7 | driver B (woken by resume + approval) | 4 | RUNNING |
| 493.4 | driver B | 4 | COMPLETED (lease row then deleted) |

* The takeover came one lease after the kill (10 s + one poll). Driver B released the dead driver's RUNNING claims
  first: `relationships` and `profile` went from claim version 1 to 3 and ran a second attempt. Every other step has
  the attempt count it has without a kill (1, and 2 for `hypotheses`, the same as in the API-mode runs on this plane).
* Leases were released at every park and claimed again on every wake, with a new epoch each time. No two drivers
  held the run at once (the lease row's holder and epoch at every change are in the JSON).
* **25/26 e2e checks.** Every check passed except `16_published_to_superset`: the `publish` step failed with
  "Superset POST /api/v1/database/ timed out". This is not an orchestration fault. Superset 6.1 syncs a permission
  for every schema of the analytics database when it creates the per-workspace connection. The shared dev
  `analytics` database holds 527 schemas from many sessions, and the publisher's request timeout is a fixed 30 s.
  The 05:43 run on the same Superset fit inside it; this one, on a host also running two drivers, did not.
  Follow-up (publishing, not ORC): a longer or configurable timeout for that call, or a reused connection.

The contract (two drivers never advance the same run, expired leases are taken over, fencing by epoch) is also
covered by `tests/integration/test_run_driver_leases.py` with two driver processes on Postgres (4 passed, 2026-10-30).
